# 项目过程报告 · M3 多模态入库（OCR）

> 所属阶段：**M3（多模态入库 OCR，原 M4 提前）**｜执行日期：2026-09-24
> 阶段范围按产品经理 2026-09-24 指令调整：RAG 部分优先做完整（扫描页/图片识别属知识库本体），Agent 顺延至 M4；本阶段由主循环亲手实现（不使用子智能体编排）。

## 1. 这阶段做了什么

- **路线图再调整**：M3（多模态入库）与 M4（Agent）内容互换，变更记录、需求覆盖映射、风险条目（R2/R5 的 M 编号）、测试树同步更新；tag 口径改为 `M3-ocr-multimodal` / `M4-agent`。
- **OCR 回填层（app/ingest/ocr.py）**：`ocr_fill_pages` 把 M2 登记的 `empty_pages` 逐页经 GLM-OCR 转文本写回 ParsedPage；页图像按格式分发——图片文件取自身字节、PDF 用 pymupdf 2x 渲染、PPT 抽幻灯片内嵌图片 blob（多图逐张识别拼接）；Word 逻辑页无图像来源保持登记。**纯文本文档零模型调用**（不查驻留、不卸载、不识别）。
- **显存互斥序列落地（本阶段红线核心）**：OCR 前经 `gateway.active_models()`（新增，查 Ollama `/api/ps`）确认 LLM 驻留——驻留才 `unload`（对未加载模型发 keep_alive=0 会让 Ollama 先加载再卸载，白等几十秒）；OCR 调用 `keep_alive=settings.ocr_keep_alive`（=0）用完即卸、`num_predict=2048`（整页识别比生成类 512 长，仍受控）、`temperature=0`；全程走 gateway 互斥锁；OCR 全部结束后流水线才向量化——时序上「OCR 与 LLM 时段隔离」自动成立。
- **流水线接入**：`parse → OCR 回填 → 切块 → 指纹 diff → 增量向量化`，顺序不可换（回填必须在切块前）；M2 的切块/指纹/增量/溯源零改动复用。
- **图片文件入库**：`.png/.jpg/.jpeg` 作为「一页空文本文档」进 parse，OCR 阶段回填——与扫描页走同一条回填路径；前端上传白名单与文案同步（含 OCR 耗时提示、失败页「重新上传可重试」）。
- **依赖与测试**：requirements 新增 `pymupdf>=1.24`（分组注释更新为 M3/M4）；新增 8 项单测（互斥时序断言 / 未驻留不卸载 / 纯文本零调用 / 失败容错 / PDF 渲染回填 / PPT 纯图页 / 图片解析 / 流水线端到端），全量 **64 passed**。

## 2. 遇到了什么问题

1. **pypdf 不能把 PDF 空白页渲染成图片**：M2 用 pypdf 只能读文本层，扫描页没有图像字节可喂 OCR——回填链路在渲染环节断了。
2. **对未驻留的 LLM 执行卸载会适得其反**：keep_alive=0 空生成对未加载模型是「先加载再卸载」，白等几十秒；盲目执行「OCR 前必卸」会拖慢所有纯文本文档的入库。
3. **OCR 整页输出超过生成类默认上限**：`num_predict=512` 会把一页扫描文档截断（识别到一半没丢，入库内容残缺）。
4. **OCR 失败的连坐风险**：一次 GLM-OCR 故障若抛穿流水线，文本层完好的文档也会入库失败（M2 设计里 parse 后任何异常都标 failed）。
5. **测试编辑错位**：连续批量编辑 test_ocr.py 时两处 old_string 因前序编辑已改变上下文而失配（工具正确拒绝），留下一个无引用的死函数。

## 3. 怎么解决的问题

1. **引入 pymupdf（`import pymupdf`）专用于渲染**：纯 pip 安装、无 poppler 之类外部二进制（Windows 答辩机部署最省事）；它只做「页 → PNG → base64」，OCR 本体仍是锁定的 GLM-OCR，技术栈零变更——依赖决策与理由写入 requirements 分组注释与 ROADMAP 风险表，供产品经理复核。
2. **先查后卸**：gateway 新增 `active_models()`（读 `/api/ps`），仅当 LLM 名（或其 `:tag` 变体）在驻留列表里才卸载；查询本身故障不阻断（OCR 自身失败走容错）。「驻留→unload→generate」的**时序被单测断言锁死**（unload 索引必须小于 generate 索引）。
3. **OCR 单独的输出上限**：`OCR_NUM_PREDICT=2048` 模块常量并在注释写明「整页识别的受控上限」——红线要求的是「输出有界」而非一律 512；`temperature=0` 保证识别确定性。
4. **失败页容错**：单页 OCR 异常只把该页保留在 empty_pages（文本不写半截），已解析文本层照常入库；纯空白页无图像来源也不白跑 OCR；前端文案从「将在多模态阶段识别」改为「识别失败/空白，重新上传可重试」——账目始终真实。
5. **复核上下文后精准删除死函数**，全量 pytest 64 passed 复验绿；教训：批量编辑同一文件时每次 old_string 必须以文件**当前**状态为基准（前一次成功的编辑会改变后续上下文）。

**阶段遗留（验收时盯）**：本阶段单测全程假网关（显存红线：单测绝不打真实 Ollama），真实 glm-ocr 的识别质量与 nvidia-smi 峰值要靠产品经理本地跑通验收——纯文本文档入库不应触发 OCR 路径；含扫描页的文档首次上传会明显变慢（属预期）。
