## 一、这阶段做了什么

1. **流式输出（打字机）**：
   - `llm.generate_stream()`：Ollama NDJSON 流逐段 yield，**queue+mutex 覆盖整段流**（红线语义不变——流式只是传输方式变化，绝不逐段放锁造成并发推理）；
   - `/chat/ask` 加 `stream` 参数（默认 false=既有 JSON，**老调用方与 163 项旧测试零感知**）；true=SSE 三事件契约 `delta / done / error`；
   - 编排：后台任务跑 `run_agent`，`on_delta` 回调直塞 `asyncio.Queue`，生成器边收边发；**done=净化后契约**（净化伪来源/资料不足闸门/拼来源全部在流完后统一执行）；落库发生在发 done 之前；
   - 双模生成收口 `_generate()`：qa/summary 有回调走流式、无回调走原 generate（单测全走非流式，断言语义零改动）；出题/计算不流（JSON 需整包解析）。
2. **溯源看原页**：`GET /kb/groups/{gid}/page-image`——PDF pymupdf 2x 渲染 PNG、图片原件直出、Word/PPT 人话 404「暂不支持」（宁可不给不给错页）；来源契约新增 `group_id`；来源折叠条内「查看原页」按钮，图片缓存 session_state（同页不重复请求）。
3. **会话导出 Markdown**：纯前端 `_history_to_markdown` + `st.download_button`（含逐条来源与相似度），零后端改动。
4. **示例问题**：空对话三枚按钮 → `pending_prompt` 注入，与 `chat_input` 同一条提问路径（不另写处理逻辑防漂移）。
5. **测试**：`tests/test_stream_page.py` 7 用例——事件序、done 落库时序、闸门在流后、error 无 done、`stream=false` JSON 回归、原页端点 200/越界 404/越权 404/格式 404、on_delta 转发+净化。

真实链路自检：demo 账号真 Ollama 流式问答——98 个 delta、拼接与 `done.answer` 一致、hit/intent/sources 正常。

## 二、遇到了什么问题

1. **`st.download_button` 同时传 `width` 与 `use_container_width`**——1.64 两参数并存但语义重叠，可能告警；
2. **测试提问用了过短的词「学习率」**——假向量得分跌破阈值走空召回，error/闸门用例测的根本不是目标路径（`['done']` 而非 `['error']`）；
3. **资料不足闸门在流式下的文案时序**：流出去的是模型原始文本，`done` 是兜底话术，两者瞬间不一致；
4. **TestClient 测不出逐字节奏**：首 delta 时间 ≈ 整段完成时间（传输层缓冲），「打字机快不快」在 TestClient 里无法验证；
5. （预防性自查）SSE 分支中 `db` 会话的生命周期——生成器执行期间依赖尚未关闭，需确认落库时序。

## 三、怎么解决的问题（与上一一对应）

1. 查 `inspect.signature` 实测后删掉 `use_container_width`，只留 `width="stretch"`（**框架 API 以本机实装签名为准**，与 M4 radio 事件同款纪律）；
2. 换用已验证命中的问法「学习率过大会怎样」，并给闸门用例加 `stub.calls == 1` 断言——**证明走到了生成环节**，杜绝「测的是另一条路径」的假绿；
3. 前端以 `done` 为唯一事实源（重跑渲染循环用 done 覆盖流上屏内容），文案归一为兜底话术；语义本就一致（都在说「资料不足」），瑕疵已注释在页面代码里；
4. 如实记录：逐字观感交给产品经理在真实浏览器验收（uvicorn+SSE 是真流式），单测只锁**事件契约**不锁时间；
5. FastAPI 依赖清理发生在响应发送完成后——SSE 正文属于响应发送阶段，生成器内落库安全；`done` 先 `_persist_result` 再 yield，前端收到即已入库（有断言守着时序）。

**遗留**：首字延迟约 11s（分类 ~6s + 预填充 ~4s + 检索 <1s）——若体验仍嫌慢，后续可把意图分类与改写合并/精简 system，属独立调优项，未在本包范围。
