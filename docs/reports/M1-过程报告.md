## 1. 这阶段做了什么

- **核心层（app/core/）**：`config.py` 配置中心（pydantic-settings 读 .env，支持 DATABASE_URL 覆盖）；`exceptions.py` 业务异常体系（统一 `{"error":{code,message}}` 出口）；`security.py` bcrypt 密码哈希 + JWT 签发/校验；`llm.py` ★ Ollama 推理网关——排队闸门 `Semaphore(1)` + 模型互斥锁 `asyncio.Lock` + `keep_alive` 驻留策略 + embedding 批量限流（16 条/批）+ 健康检查，这是 8G 显存红线的代码落点。
- **数据层（app/db/）**：SQLAlchemy 会话（生产 MySQL / 单测 SQLite 内存库可切换）；`users` 表模型（user_id 为全库数据归属锚点）；用户 CRUD（唯一冲突翻译为 409 人话）；`scripts/init_db.sql` 幂等建库建表（utf8mb4）。
- **接口与入口**：`/auth/register`、`/auth/login`（签发 JWT）、`get_current_user` 依赖、`/health` 健康检查（一次看清鉴权 + Ollama 连通 + 三模型在列）；`scripts/check_ollama.sh` 环境自检脚本。
- **测试**：新增 14 项单测（JWT 往返/过期/伪造签名拒绝、密码加盐、**并发推理串行化守卫**、keep_alive 传递、embedding 批量限流、用户 CRUD/唯一约束），全量 19 passed（含 M0 冒烟）。
- **验收与交付**：真 MySQL 全流程 7 用例验收（注册/重复注册/登录/体检/无 token/错密码/坏参数）；check_ollama.sh 确认三模型在列、显存基线 2240/8188 MiB；分 4 次提交推送，打 tag `M1-infra`。

## 2. 遇到了什么问题

1. **`ollama pull glm-ocr` 拉取失败**：报 `net/http: TLS handshake timeout`，manifest 成功但权重 blob（R2 存储）下载超时。
2. **SQLite 下 `BigInteger` 主键不自增**：单测插入用户报 `NOT NULL constraint failed: users.id`（MySQL 上 BIGINT 自增正常，SQLite 只有 INTEGER PRIMARY KEY 才是 rowid 别名）。
3. **异常翻译过宽掩盖真 bug**：`crud.py` 把所有 `IntegrityError` 都译成「用户名已被注册」，把问题 2 误报成业务冲突，拖慢排查。
4. **错误响应格式不统一**：无 token 请求被 FastAPI 的 `Header(...)` 必填校验抢先拦截，返回默认 422 `{"detail":[...]}` 而非统一 `{"error":{...}}`。
5. **模型名过长与 .env 不一致**：镜像拉取得到的模型名为 `modelscope.cn/ggml-org/GLM-OCR-GGUF:latest` 等长名，与配置中的 `glm-ocr` / `qwen3-embedding:0.6b` 不匹配。
6. **冒烟残留进程**：一次冒烟的 uvicorn 进程未退净，SQLite 临时文件被占用（`Device or resource busy`）。
7. （小插曲）`ollama tag` 命令不存在，报 `unknown command "tag"`。

## 3. 怎么解决的问题

1. **系统化调试（先根因后修复）**：分层连通性探测证明——`ollama.com` 清单服务器正常、R2 权重主机 DNS 超时；换阿里 DNS 能解析出真实 IP 后，**强制 IP 直连 TCP 仍超时 → 定性实验否决「改 DNS」方案**，确认为链路级封锁。修复：改用 ModelScope 的 Ollama 镜像源成功拉取（产品经理操作）；备用方案（hf-mirror 下载官方 GGUF `ggml-org/GLM-OCR-GGUF` + `ollama create`，含 mmproj 视觉投影层）也已验证可用并留档为 fallback。
2. 采用 SQLAlchemy 官方的**方言适配**写法：`BigInteger().with_variant(Integer, "sqlite")`——生产 MySQL 保持 BIGINT（与 init_db.sql 一致），SQLite 单测自动退化为可自增的 Integer，并在注释里写明原因。
3. **精确化异常翻译**：只有错误详情含 `unique`/`duplicate`（SQLite/MySQL 两家的唯一冲突报文关键词）才译成 ConflictError，其余完整性错误如实上抛——真 bug 不再被业务话术掩盖。
4. 统一错误出口补全：`Header` 改为可选声明、缺失时抛 `AuthError`（401 统一格式）；`RequestValidationError` 也并入 `{"error":{...}}` 格式（422 统一格式），前端只需一个解析函数。
5. 用 `ollama cp` 为长名模型建立**短名别名**（共享底层数据零磁盘复制），与 `.env` 配置对齐，代码零改动。
6. 用 `netstat + taskkill //F //T` 清理残留进程；后续冒烟统一 `kill -9` + 端口复查。
7. 不猜命令：`ollama --help` 查证后改用 `ollama cp`（教训：命令不确定就查 help，不瞎试）。

**方法论小结**：本阶段最有价值的实践是「定性实验否决便宜但错误的方案」——「改 DNS」看似顺理成章，强制 IP 直连一个实验就将其否决，避免了无效折腾；以及「异常翻译过宽会掩盖真 bug」的教训，已在代码注释中留档。
