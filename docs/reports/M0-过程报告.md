# 项目过程报告 · M0 项目骨架与协作规范

> 所属阶段：**M0（项目骨架与协作规范）**｜执行日期：2026-09-22｜本报告于 2026-09-23 补写

## 1. 这阶段做了什么

- **整体规划与架构决策**：完成 7 项关键架构选型并写入文档（ChromaDB 嵌入式向量库、LangGraph+显式意图分类、asyncio 推理闸门、OCR 显存互斥与 `keep_alive` 三级策略、两级 sha256 增量指纹、记忆双写、三层防幻觉溯源），每项都给出备选对比与「为什么」。
- **文档三件套**：`README.md`（技术栈清单 + 生产环境 vs 毕设降级 9 行对比表）、`CLAUDE.md`（协作契约：角色分工/五步节奏/8G 显存红线/git 门禁）、`docs/ROADMAP.md`（完整目录结构树 + M0–M8 开发路线图）。
- **工程骨架与冒烟测试**：搭建 app/frontend/tests/scripts/config 目录树；`tests/test_smoke.py` 5 项测试把「结构契约」（文档存在/配置键完整/依赖栈锁定/对比表覆盖/协作规则在档）固化成自动化守卫。
- **仓库初始化**：`git init` 绑定 `git@github.com:lkk157/ZhiYuan_EduMind.git`，配置 `core.autocrlf input`、`core.quotepath false` 防 Windows 坑；分 6 次提交推送，打 tag `M0-skeleton`。
- **OCR 选型定档**：视觉/OCR 模型经两次变更后定为 **GLM-OCR（glm-ocr）**（产品经理书面确认），README/CLAUDE.md/.env.example/ROADMAP 四处同步更新。
- **环境核验**：确认本机 LLM 实际名称为 `qwen2.5:7b-instruct-q4_K_M`（非印象中的 `qwen2.5:7b`）；对 glm-ocr 做真图视觉冒烟（喂入含 `E = mc^2` 公式的测试图，逐字正确识别）。

## 2. 遇到了什么问题

1. **工作区是完全空目录**：需求文档（《知源项目需求文档》）不在仓库内，也未在周边目录找到文件。
2. **模型名与印象不符**：`ollama list` 中实际是 `qwen2.5:7b-instruct-q4_K_M`，与配置准备写的 `qwen2.5:7b` 不一致。
3. **OCR 选型两次变更**：需求最初写 DeepSeek-OCR-2 → 确认改为 DeepSeek-OCR → 最终拍板换 GLM-OCR，涉及多份文档同步。
4. **Windows 控制台 GBK 编码崩溃**：视觉冒烟脚本最后打印时抛 `UnicodeEncodeError: 'gbk' codec can't encode character '✅'`（emoji），脚本中断（此时模型识别本身已成功返回）。
5. **在线检索工具不可用**：无法直接查询两个 OCR 模型的公开资料对比。

## 3. 怎么解决的问题

1. **需求以对话中的需求文档为准**，全部内容结构化沉淀进 README/CLAUDE.md/ROADMAP 三件套，规划产物先经产品经理确认再落地（本项目五步节奏的首次完整执行）。
2. 确立原则「**模型名以 `ollama list` 输出的 NAME 为准**」，写入 CLAUDE.md §5 与 `.env.example` 注释，配置里直接采用实际标签——此后所有模型配置沿用该原则。
3. 走「技术栈变更需产品经理书面确认」流程，确认后一次同步修改 4 个文档 + 本地 `.env`，并把 fallback 链（deepseek-ocr → qwen2.5-vl:3b）写进风险预案；模型页事实用 curl 直探 ollama.com 官方库取证（GLM-OCR 2.2GB vs DeepSeek-OCR 6.7GB，8G 显存下体积是压倒性优势）。
4. 日志与脚本输出避免 emoji/特殊符号，文件读写强制 `encoding="utf-8"`，写入 CLAUDE.md §5 作为长期约定（后续 M1 的日志配置沿用）。
5. 改用「curl + Python 直探官方页面/API」的分层探测法拿到模型事实——这套分层排查思路直接复用在 M1 的网络根因调查中（见 M1 过程报告）。
